## 3. Where GF's clips come from (CONFIRMED by the counters and the start histogram, INF for the PES mechanism)
1. **Placement.** `HumanoidBase::ResetPosition` puts GF's idle clip on the man and leaves his MoveStepRecord where it was (`MoveStepRecord::EnterInit` had NO caller anywhere). A record left in IDLE with `liveKind == kind` issues nothing (IDLE handler, `movestep_group_a.cpp`: "if live kind == kind: only IDLE_OTHER exits"), so the man keeps GF's idle clip for good: the 142k IDLE ticks. PES: the action switch calls `FUN_1406EB440` on every action entry, which clears the phase (`P+0x245D = P+0x245C; P+0x245C = 0`, `pes-re-gaps-anime.md` 387), so a MOVE entry starts MOVESTEP in INIT, whose handler issues the first clip; a placement is PES's reset `FUN_1406EE6A0` (exit the current action).
2. **End-of-clip switch (`Humanoid::Process`).** A MOVESTEP-issued clip that reaches its last frame is replaced by a GF clip, whatever the state. PES's anime player holds the motion: "loop clips the player holds" (`pes-re-anim-blend.md` 1.2, 5.2); the IDLE handler issues again only when the request changes. After the first PES-to-GF switch the FSM never issues again while its live kind is unchanged, so the GF clip chain (GF-to-GF starts: 9,614 idle, 3,135 autogen, 1,237 sprint on the base) never ends.
3. **AnimeState stand-in.** `MoveHostAdapter::AnimeState` answered 0 for a MOVESTEP locomotion clip (a Special function), so every PES issue counted as an action change against the GF clip's 2 and re-ran the action-entry stores.
