## 1. The null dispatch (CONFIRMED by gdb backtrace)

`gdb -batch -ex run -ex bt` on `pes_stall_test`: `abort <- pes_dispatch_missing <- pes_fn_141EB39A0 <- pes_fn_14079C2D0 <- pes_fn_140795AB0 <- pes_fn_140795A40 <- Match::Process`. `FUN_141EB39A0` (`0x141EB39A0`) is called with rcx = **P+0x428** (`0x14079CF4x`: `lea rcx,[rsi+0x428]`, rsi = P); it loads the vtable word at `[rcx]` and calls vtable slot `+0x10`. GF never wrote that word, so the dispatch target was 0.

P+0x428, P+0x498 and P+0x4D0 are the three vtable words of the member object that the constructor **`FUN_141EB42B0` builds at P+8** (param_1 = P+8: its store at param_1+0x420 is the word the captures hold at P+0x428; CONFIRMED against all 14 captures, no derived-byte mismatch). The oracle had masked this: its overlay copies the capture's bytes into every window byte GF left zero.

Fix: `pes::ConstructActorP(world, slot, constants)` (pestrapactor.cpp), the constructor's non-zero stores, called once per slot at match start (`match.cpp`) and in the oracle's `Build`. Constants read from the install behind opcode checks (`LoadActorConstants`): the three `lea rax,[vtable]` sites `0x141EB4375/0x141EB43CF/0x141EB43F8` (`48 8D 05`), the rate numerator `movss xmm1,[0x14256AE1C]` at `0x141EB4333` (`F3 0F 10 0D`; P+0x41C = numerator / tick rate). Layout constants with VA citations in pestrapworld.hpp (`kMember*`): u16 `0xFFFF` at +0x474/+0x476/+0x478, f32 -1.0 / 1.0 at +0x484/+0x488, u16 `0xFF00` at +0x4F8, 38 unit-table 1.0 cells (+0x6F8 stride 0x10, +0xC), 40 f32 1.0 from +0x958, f32 1.0 at +0x9F8, u32 `0x10001` at +0x9FC (all from param_1). Also the P-tail stores of `FUN_1406E03D0` (`0xFFFFFFFF` at P+0x3B50/0x3B7C/0x3BBC, f32 1.0 at P+0x3B5C/0x3BB4).

Evidence the port is right: with it on, the tick oracle's derived-byte check (a byte GF wrote that differs from the capture) reports nothing on any of the 14 captures, and `TrapOracle` (kind 0, TrapOpen's 24 dirs) is 7/7 on the tests I ran (`EachWindowBindingChangesTheCall`, 256 s, not rerun).

## 2. What `pes_stall_test` does now (CONFIRMED by gdb)

Second run, after the constructor fix: `PES_DISPATCH_UNTRANSLATED: 0x1406eebb0` from `pes_fn_14079E5C0 <- pes_fn_140796CE0 <- Match::Process`. `0x1406EEBB0` is the **action switch** (decompiled this session): the trap's end-of-action handler (`0x14079E5C0`, three sites: lines 154, 211, 369 of the translated unit) calls `switch(P, 2 = MOVE, sub = 0x5E)`. The switch calls the action table's objects (`FUN_1406D9010(P+0xC40, id)` vtable +0x28 exit / +0x18 enter, the `P+0xAB8` interface vtable slots +0x28, +0x78, `FUN_14081E340`, `FUN_1406EB440`, `FUN_140A6E340`, ...): PES's per-action objects that GF does not have. It is outside the translated set (`pes_dispatch_missing(0x1406EEBB0)` is hard-coded by the generator for out-of-set calls), so a match in which a man finishes a trap aborts. The third stall run (after the P extension below) was started; its result is in the final message.

This is a design decision, not a bug: either (a) extend the closure to the switch and the action table (large: every action's enter/exit), or (b) a named GF stand-in for the switch's observable effect on P (stores `P+0xACA/0xACB <- 0xAC8/0xAC9`, `P+0xAC8 = new`, `P+0xAC9 = sub or new`, `P+0xB08 = 0`, and hands the man back to GF's movement), registered through `tools/dev/translate/stubs.json` (the generator's stub-model mechanism, `pes_stubs.hpp`) with a `ponytail:` naming `0x1406EEBB0` as the PES site that removes it. I did not choose (b) without the owner: the brief says never stub a call, and this one is not a null pointer. **Main decides.** Also needed with it: the `0x14079D4B0` out-of-set call on the other branch of the same handler.
