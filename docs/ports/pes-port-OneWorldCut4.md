## 1. Item 1: the BodyAnimControl seam (the table writer FUN_141EB4650), step 1 done

### 1.1 The finding that decides the design (CONFIRMED)
- Running the player constructor FUN_141EB5250 (`PesFoxWorld::ConstructAnime`) in place on the window's P aborted with `PES_DISPATCH_UNTRANSLATED: 0x14239EF20` (same trace as the E1 verdict: 141EB5250 -> 141AFB090 -> 1423A2090 -> 1423A0DE0), while the same call on a heap block ran. Main's reading (P must be a PES-heap allocation) is NOT the cause. Measured:
  - A temporary read-only print in `pes_fn_1423A0DE0` at the load of `*(state+0xE8)` (state = r14, descriptor = r15): on the heap run `descriptor[+0x28]` = 0x3000f10110 (a resource object in the OS arena) and `*(state+0xE8)` equals it; on the window run both are 0. The resource is found by FUN_141B03540 through the clip database cell 0x1437CEAA0 (identical in both runs: 0x2400044420), through the constructor's reads of the player block.
  - The block's bytes are not the cause: zeroing the whole 0x3C00 bytes first (window run) still aborted. A dummy 0x3C00 heap allocation before the construct (to equal the heap run's allocation order) still aborted. So neither content nor allocation order.
  - The cause is a mapping omission: `PesMemory::NewCall()` (the engine's call state) mapped the image, heap, stack, TEB and OS arena but NOT the match's window (the trap world's calls map it themselves, through `PesWorld::NewCall`). A fox call on a window VA read zeros and dropped its writes.
- What the constructor writes into its block (CONFIRMED, nonzero dwords of a heap block after construction): P+0xA04 = 1, P+0xA08 = the control (8 bytes), P+0xA10 = "body", P+0xA20 = 4, P+0xA28 = 0xF, P+0xAA8..0xAB4 = four 0xFFFFFFFF. Nothing else of the 0x3C00 block.
- Back-pointers (Main's question 1): not copied, so moot. The block is constructed in place on the window's P; no heap copy exists. (A scan of the control for the P address was not needed once the construction is in place.)

### 1.2 The fix (commit `0f47414d`)
`PesMemory::AddWindow(va, bytes)` records the match's window and every `NewCall()` maps it (`pesmemory.{hpp,cpp}`); `PesWorld::BindMemory` passes `kWorldWindowVa` (`pesworldrecord.cpp`).
Tests (`tests/pes_fox_template_test.cpp`, new): `ACallOfTheMemoryReadsAndWritesTheMatchWindow` (a call reads the host window's bytes; its write lands in them) and `ThePlayerConstructorBuildsTheControlOnABlockInTheMatchWindow` (the fields 0xA04..0xAB7 equal a heap block's except the control's address; the control's vtable equals the heap one's). Red: the same construct on a window block aborts at 0x14239EF20 (measured above, before the fix). Mutation (run, rebuilt, reverted): dropping the mapping line fails the first test (2 failures) and aborts the second at 0x14239EF20. Green with the fix: 2 of 2.
