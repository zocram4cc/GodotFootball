## Cut 2 (`f48f14ce`): the booted anime world is a frozen template; each match's world is a copy-on-write clone

Why the clip-database write breaks (CONFIRMED unless marked INF). It is not the judge that breaks: the first tick aborts in the anime player's construction, before any foul is judged. The loader writes its clip-database object to the global cell 0x1437CEAA0 (`pesanimechain.cpp:247`, `out.globals`), where PES's boot had put the booted ResManager (the cell is `DAT_1437CEAA0`, set by FUN_141B02800; `pesfoxworld.cpp`). So the write replaces the ResManager pointer in that cell with GF's object. The anime constructor's chain reaches `FUN_1423A0DE0` (translated, `src/pes/translated/closure/pes_fn_1423A0DE0.cpp`): it loads `*(obj+0x60)`, and when that is zero it takes the `z` arm, which ends in a direct call to `0x14239EF20`. That call is out of the translated set, so the translator emits `pes_dispatch_missing(0x14239EF20)`, and the run aborts. The GF-built object writes only its pack count (+0x18) and packs pointer (+0x20) (`pesanimechain.cpp:201-202`), so +0x60 stays zero. INF: the booted ResManager has +0x60 set (implied by normal runs, which never take that call). INF: that `obj` is the object in the cell; the branch and the call are read from the code, and the object's identity is inferred from the cell and from the abort appearing only in runs that wrote it. The check that settles it: trace `gpr14` at `FUN_1423A0DE0`'s entry in a clip-database run and compare its +0x60 with the booted ResManager's.
