## 4. Why the graph is not built in GF (OPEN, exact blocker; no stand-in written)

Measured by running PES's bytes on the synthetic ctor state and recording first-touch reads (`py/rdset.py`, scratch): **the constructor reads 44,627 bytes it did not write, 1,739 in the image and 42,888 elsewhere, in ~150 groups.** They are the LOADED fox entity graph of the "body" resource, not data GF holds: R and its three `fox::gr::Model` objects (R+0x20/+0x78/+0x110: 92-byte groups at Model+0xA0 etc.), `anim::PoseOperatorMirror/RootRot` property blocks (472 B x4, 632 B, 256 B...), `HandlerT<Entity>` property handler blocks (~4 kB), `MtarFile` headers (the .mtar bytes GF already holds verbatim), `HavokFileLoader`, and a 32,616-byte `FileCallback` region. About 60% of the non-zero 16-byte chunks of one man's IK parameter blocks (HumanLegIk / SlantIk / LookAtIk) also occur verbatim in the image (INF: image-resident property defaults), the rest comes from the entity data, so neither the image nor GF's rig supplies them.
These objects are made at boot by the FoxAni resource loader: FUN_141EC86D0 (registry insert; "cpk_dat/common/demo/anime/FoxAni...", "Project.hkx") -> FUN_141AF7AB0. `closure.py --dry-run`: **922 direct members from FUN_141AF7AB0, 963 from FUN_141EC86D0**, plus vtable targets, file IO and job threads. That is the next slice (translate and prove the loader on real captures of FUN_141EC86D0 / FUN_141AF7AB0, which run once per boot: they need a hook armed before the pre-match load), not something to hand-build: a hand build would have to invent ~43 kB of entity data.
